# Заявки, бинарные вложения и уведомления

## Изменения

Новые заявки, нормализованные файлы (PostgreSQL BYTEA) и задача уведомления сохраняются одной вложенной операцией Prisma. HTTP-контракт `/api/inquiries/` не изменён. API не ожидает SMTP. Успех формы означает сохранение в БД.

Модели `Application`, `ApplicationFile`, `NotificationJob` используют `@@map` на существующие таблицы `Inquiry`, `InquiryFile`, `Notification`. Идентификаторы, заявки, доказательства согласия и старые файлы сохраняются. Миграция `202611250001_binary_files_outbox` добавляет BYTEA и токен аренды; она не переносит и не удаляет существующие файлы. `storageKey` остаётся для чтения старого закрытого хранилища. Бинарное поле глобально исключено из стандартных запросов Prisma; чтение выполняет `src/server/application-files.ts` с явным select и проверкой размера/хеша.

## Включение

1. Утвердить политику, отдельное согласие, срок хранения, получателей, договоры с российскими хостингом/почтой и порядок удаления копий. Проекты в `src/content/operator.ts` не являются действующими документами.
2. Указать пути и версии утверждённых документов, `LEGAL_DOCUMENTS_APPROVED=true`, согласованный `INQUIRY_RETENTION_DAYS`, секрет формы и российскую PostgreSQL.
3. Подключить рабочий ClamAV/clamdscan и обновление сигнатур. Для включённой production-формы `UPLOAD_SCAN_REQUIRED=true` обязателен. Исходные и нормализованные байты проверяются до записи в БД. Временные файлы создаются с правами 0600 в закрытом каталоге и удаляются после проверки. После аварийного завершения их удаляет cleanup. Нет сохранения загрузок в public.
4. Настроить SMTP и `PROJECT_MANAGER_EMAIL`. Получатель пока намеренно не задан. Старый `MANAGER_EMAIL` поддерживается для совместимости, но новый параметр имеет приоритет; старое значение нужно удалить при переходе.
5. После отдельного разрешения и проверенной зашифрованной резервной копии применить миграции на целевой базе. До этого развёртывать новый код поверх старой схемы нельзя. В этой работе production-миграции не выполняются.

Начальные лимиты: 5 файлов, 10 МиБ каждый, 20 МиБ суммарно. Можно уменьшить по возможностям VPS/прокси. Расширения, MIME, сигнатуры, декодирование изображений и проверка активного содержимого PDF остаются обязательными. Срок хранения не имеет выдуманного значения по умолчанию: без явной настройки форма отключена.

## Очередь и SMTP

Запускать `npm run inquiries -- notifications` каждую минуту через cron/systemd timer, `npm run inquiries -- cleanup` — каждый час. Нужна полная серверная установка проекта с tsx. Не запускать воркер только в памяти процесса Next.js. Шаблоны systemd находятся в ops/systemd: перед установкой согласовать пути, создать Linux-пользователя formresurs, каталог var с правами 0700 и защищённый runtime.env. Шаблоны не устанавливаются и не включаются автоматически. Для ClamAV/старого UPLOAD_DIR вне var дополнительно согласовать права и ReadWritePaths.

`NOTIFICATION_MAX_ATTEMPTS=8` ограничивает попытки, включая отсутствие SMTP и истёкшие аренды после сбоя воркера. Задержка растёт экспоненциально; после лимита статус FAILED. Для ручного возобновления после устранения проблемы: `npm run inquiries -- retry-notifications`. Команда фиксируется в аудите. Рекомендуется мониторить PENDING/RETRY/NOT_CONFIGURED/FAILED, не публикуя содержимое заявок.

Атомарный захват, счётчик попыток и индивидуальный leaseToken защищают состояние задачи от параллельных воркеров. Аренда — 60 секунд, SMTP ограничен тайм-аутами. После истечения аренды задача может быть перехвачена. Запись SENT/sentAt означает только подтверждённое принятие настроенным SMTP-сервером для целевого адреса. Это не подтверждение попадания во входящие, окончательной доставки или прочтения. При неизвестном исходе SMTP возможен повтор; стабильный Message-ID не является гарантией дедупликации.

В письме: UUID заявки, дата UTC, имя, организация, телефон, email, услуга и задача. Вложения включаются только если оценка полного MIME-размера с base64 и запасом укладывается в `SMTP_ATTACHMENT_MAX_MB` (по умолчанию 10 МиБ). Для больших файлов письмо содержит команды закрытого доступа по SSH, а не публичные ссылки. Нужны индивидуальные SSH-ключи и явно предоставленные оператором права. Веб-админка и публичная выдача файлов не добавляются.

## Закрытый доступ и старые файлы

`list` не выводит контакты. `show` выводит данные только в защищённую операторскую консоль; не перенаправлять вывод в общедоступные журналы. `file` проверяет принадлежность файла заявке, срок действия и хеш, создаёт файл 0600 без перезаписи. Каталог назначения должен существовать с правами 0700 и не находиться в public/out/.next, включая переходы через symlink.

~~~bash
npm run inquiries -- list
npm run inquiries -- show APPLICATION_UUID
npm run inquiries -- file APPLICATION_UUID FILE_UUID /закрытый/каталог/document.pdf
~~~

`npm run inquiries -- migrate-files` предназначен для отдельного согласованного переноса старых данных: обрабатывает до 25 записей за запуск, проверяет размер/хеш и антивирус, записывает BYTEA и аудит, не удаляет исходники. Повторный запуск пропускает уже перенесённые записи. **Не выполнять на реальных персональных данных без отдельного разрешения.** После сверки и утверждения процедуры удаления копий оператор отдельно удаляет лишние старые файловые копии; код не делает этого автоматически. До тех пор они входят в контур защиты и резервирования.

## Удаление

`npm run inquiries -- delete APPLICATION_UUID` закрывает доступ по expiresAt, отменяет задачу уведомления, удаляет старые файловые копии при их наличии, а затем транзакционно удаляет заявку с бинарными вложениями/задачей по CASCADE и пишет аудит без контактных данных. Если старый файл удалить не удалось, запись остаётся закрытой для повторной очистки. Cleanup использует тот же путь.

SMTP не предоставляет команд удаления писем. Оператор должен отдельно найти копии в почте по UUID/Message-ID, удалить их согласно утверждённому регламенту и учесть архивы, почтовые резервные копии и выгруженные сотрудниками документы. Уже отправленное или находящееся в передаче письмо невозможно гарантированно отозвать удалением строки БД. Подтверждение удаления заявки не означает удаления всех копий в почтовой инфраструктуре.

После восстановления БД из резервной копии до включения сайта нужно повторно применить согласованный реестр удалений: старый бэкап может вернуть ранее удалённые данные. Сроки и способы хранения такого реестра, аудита и бэкапов утверждает компания; значения здесь не задаются.

## Российский VPS

- Основная БД, временные файлы проверки, старое хранилище и резервные копии — на согласованной инфраструктуре в РФ. Отдельно проверить почтового провайдера и все копии. Фактический провайдер пока не определён.
- Node.js >=24, PostgreSQL, HTTPS-прокси с действительным сертификатом, ClamAV и планировщик. Ориентир для небольшого потока: от 2 vCPU, 4 ГБ RAM (ClamAV потребляет память), SSD с запасом для БД, WAL и зашифрованных копий; это техническая оценка, не гарантия нагрузки.
- PostgreSQL не открывать наружу. В compose.yaml публикация уже ограничена 127.0.0.1:5432. Дополнительно firewall, SCRAM, отдельные сильные пароли; runtime-роль без SUPERUSER/CREATEDB/CREATEROLE/DDL, миграции выполняет отдельная роль. Ограничить доступ к .env, SSH, CLI и backup credentials. Для отдельного DB-хоста — закрытая сеть и проверяемый TLS.
- Next.js слушает loopback, перед ним HTTPS-прокси. Ограничить тело запроса минимум до согласованных 20 МиБ + 128 КиБ (пример: 21m), время чтения и одновременные загрузки. Согласовать лимиты с памятью: валидация/декодирование и Prisma используют буферы в памяти.
- Не логировать тела заявок, контакты, вложения, SMTP credentials и строки подключения. Не включать отладочное SMTP-логирование. Секреты не попадут в клиентский bundle при использовании серверных модулей.
- Резервирование: `scripts/backup-postgres.sh` передаёт поток pg_dump непосредственно в age, без временного открытого дампа. Требуются pg_dump совместимой версии, age, закрытый PGSERVICEFILE/PGSERVICE с учётной записью резервирования, BACKUP_DIR и публичный BACKUP_RECIPIENT. Файл пароля/pg_service.conf — 0600; приватный age-ключ хранить отдельно от VPS. Скрипт сам резервные копии не планирует и не удаляет: график/сроки утверждаются отдельно. Хранилище копий и ключи — в согласованном контуре РФ. Проверять восстановление в изолированной среде до production-развёртывания.
- HTTPS, firewall, учётные записи, антивирус, расписание, шифрование дисков и реальное хранение в РФ требуют настройки VPS оператором. Из кода нельзя подтвердить их наличие у ещё не выбранного хостинга.

## Переменные

Новые: PROJECT_MANAGER_EMAIL (пустой), SMTP_ATTACHMENT_MAX_MB (10), NOTIFICATION_MAX_ATTEMPTS (8), LEGAL_DOCUMENTS_APPROVED (false).
Изменены начальные UPLOAD_MAX_FILE_MB=10, UPLOAD_MAX_TOTAL_MB=20. INQUIRY_RETENTION_DAYS теперь обязателен для включения формы и не имеет значения по умолчанию. Остальные SMTP/DATABASE/FORM_SECRET/PRIVACY/SCAN-параметры сохраняются. Для скрипта бэкапа отдельно нужны PGSERVICE, PGSERVICEFILE, BACKUP_DIR, BACKUP_RECIPIENT.

## Проверки

~~~bash
npm run db:generate
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
~~~

Интеграционные тесты принимают только отдельную TEST_DATABASE_URL с именем базы, заканчивающимся на _test, и создают синтетические данные. Без неё тест пропускается. Не задавать production DATABASE_URL в качестве тестовой. SMTP-проверка использует локальный тестовый TLS-сервер и сертификат TEST_SMTP_CERT/TEST_SMTP_KEY, доверенный через NODE_EXTRA_CA_CERTS; реальные адреса не используются.
